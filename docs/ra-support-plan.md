# RAを最優先とするサイト別抽出対応

更新日：2026-11-08
状態：企業名・募集職種の抽出と求人票判定は利用者提供の実画面で1件確認。応募資格・勤務地の区画抽出を追加し、今回の修正は実ページでの再確認待ち。

## 対応の優先順位

今回の転職活動で最も利用頻度が高いリクルートエージェント（RA）を、最初のサイト別対応対象とする。doda専用対応はRAの対応後に進める。

対象は、利用者が実際に開いているRAの個別求人票である。公開求人ページとログイン後の求人詳細ページの構造が同じであるとは仮定しない。まず、普段使用している画面のドメイン・パスとDOMを確認する。

## 共有情報と今回の実装範囲

- 対象URL：HTTPSの `mypage.r-agent.com/joboffers/数値ID`。求人一覧や別サイトでは専用抽出を適用しない。
- 企業名：`p` のクラストークンが `JobInformation_corpName__` で始まる要素。
- 職種：`h1` のクラストークンが `JobInformation_title__` で始まる要素。
- 応募資格：`MidSection_categoryTitle__`クラスのh3「求める能力・経験」。親sectionのaria-labelledbyにそのh3のIDが含まれることを確認し、直下の`MidSection_categoryDesc__`本文を取得。
- 勤務地：`MainSection_title__`クラスのh2「勤務地」と対応するsection直下の`MainSection_contents__`内に限定する。配属先・転勤の子sectionは、そのh3とのaria-labelledbyの対応を確認して除外する。
- Reactが生成するIDの値は固定しない。sectionとの参照関係を使う。対応する本文がない・異なる候補が複数ある場合は専用抽出で未取得と理由を残し、同じ項目の広い共通抽出を抑止する。
- クラス名末尾の生成文字列やインラインstyleの値には依存しない。
- 表示されている候補が一意の場合に取得し、複数の異なる値がある場合は決め打ちしない。非表示・nav・aside・footer内の候補を除く。
- 職種用の要素を確認できた場合に、その画面の企業名候補を取得する。企業名だけから個別求人を組み立てない。
- 読み取り根拠にRAと要素のクラス名を記録し、既存の確認・修正画面へ引き渡す。
- 求人票の判定は既存の共通ルールを維持する。2項目だけで判定を求人票に引き上げない。

仕事内容・給与・雇用形態は既存の共通処理を使う。勤務地の住所欄の内部構造は未確認であり、再現HTMLの住所やその内部の区画は合成である。今回の勤務地対応は確認できた配属先・転勤区画の除外と親section境界の制限であり、住所だけへの完全な正規化ではない。

サイト別ルールは、Chromeへシリアライズされる `extractPage` 関数内の `siteAdapters` に置いた。注入先で未解決のimportや外側の変数に依存せず、ホスト・個別求人パス・項目クラスの組合せで拡張する。

## 実装方針

- 右クリックしたページのURLと画面の構造から、対象のサイト・画面種別を判別する。
- 企業名・募集職種・仕事内容・応募資格・勤務地・給与・雇用形態を、同一の個別求人に属する範囲から取得する。
- 共通のJobPosting解析と、RAの表示内容からの抽出を照合する。構造化データの有無や形式は実ページで確認する。
- 企業名・職種の見出し位置を、全サイト共通のh1解釈に依存させない。
- サイト別の抽出結果を、既存のfields・source・evidence等の共通形式に変換する。
- RAに固有のDOM・セレクターはサイト別抽出処理へ閉じ込め、3区分判定や確認画面へ持ち込まない。
- 対応していない画面や根拠不足のページは無理に確定しない。取得できた項目と不足を既存の確認画面に表示する。
- 元の抽出値と利用者の修正値を分離する既存の仕組みを維持する。

## 実装前に確認する情報

1. 個別求人票のURLのドメインとパス。認証情報・個人識別用のクエリパラメーターは不要。
2. 企業名と募集職種が記載された要素、およびその周辺・親要素のHTML。
3. 募集要項・仕事内容・勤務地・給与等のラベルと本文の対応関係。
4. DOM上のapplication/ld+jsonとJobPostingの有無。存在する場合はtitle・hiringOrganization・descriptionとの対応。
5. 求人一覧・関連求人・紹介会社名が、個別求人の雇用主や職種に混ざらない構造か。

スクリーンショットは位置の確認に使用できるが、DOMの抽出条件の確定にはHTMLを照合する。実データをテスト化する際は、アカウント情報・トークン・個人情報を除き、企業名や求人内容を架空の値へ置き換える。

## 実装箇所と今後の対象

| 箇所 | 実装・今後の対象 |
|---|---|
| extension/extract-page.js | 自己完結した注入関数内のsiteAdaptersとサイト別見出し抽出を追加 |
| tests/fixtures/ra-header.html | 共有された企業名・職種の2要素を架空の値で再現。実ページ全体や一覧の再現HTMLは今後追加 |
| tests/fixtures/ra-sections.html | 共有された見出しと親sectionの構造に基づく再現。本文・勤務地の住所欄の内部は合成 |
| tests/ra-extract.test.js | 企業名・職種の分離、URL制限、クラス名変化、重複候補、区画の対応関係、隣接項目の混入防止を検証 |
| tests/browser-smoke.js | 抽出結果から確認・修正・再判定までの連携を検証 |
| README.md・仕様文書 | 実装・検証できたRA画面の範囲と制約を記載 |

セレクターやURL判別条件を推測だけで実装しない。拡張がページへ注入する関数は現在自己完結しているため、通常のモジュール分割だけでなく、Chromeの注入先でも依存関係が動作することを検証する。

## 完了条件

- 普段利用するRA個別求人票から、企業名と募集職種を取り違えずに取得できる。
- 取得元と根拠を表示し、元の抽出値を修正・再判定後も保持できる。
- 給与・勤務地の欠落のみで対象外にならない。
- 求人一覧・関連求人・一般ページの情報を個別求人へ混ぜない。
- RA再現用HTMLと既存テストが成功し、実際のRAページで右クリック起動から確認画面までを検証する。
- 実ページ検証と合成ページのテスト結果を区別して記録する。

Google Sheets API連携・外部企業調査・LLM分析は今回のRA抽出対応に追加しない。既存Spikeは変更しない。
