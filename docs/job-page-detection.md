# 求人調査MVP：求人票の抽出・判定・確認仕様

作成日：2026-11-07
状態：初回MVPのコード実装済み。検証結果と残る確認は [implementation-status.md](implementation-status.md) を参照。

追加フェーズ：利用者の希望によりOllamaによるローカル分析を追加した。以下の「初回実装範囲」は初回MVP時の範囲として保持し、追加機能と接続先の仕様は [local-llm-analysis.md](local-llm-analysis.md) に定義する。外部LLM API・外部企業調査・Sheets登録は引き続き対象外。

## 1. 目的と開発方針

ブラウザで表示中の個別求人票を、右クリックメニューから取得し、求人票かどうかの判定と抽出内容の確認・修正を行う。

Google検索ページのMHTML保存機能は、既存の `spike/` に技術検証として残す。
求人調査MVPは、同階層の `job-research-mvp/` に別のChrome拡張として作成する。Spikeのコード・権限・画面・検証データは変更しない。

別ディレクトリを採用する理由は、検索保存機能への影響を避け、求人票の抽出・判定を独立してテストでき、
将来の企業調査や登録処理を追加しやすくするためである。MHTML保存処理は初回実装には不要なため、コピーや共通ライブラリ化を行わない。

サイト別抽出はRA（リクルートエージェント）を最優先とする。共有されたRA個別求人の企業名・職種要素に初期対応し、共通の3区分判定へ引き渡す。対応範囲と残る確認は [ra-support-plan.md](ra-support-plan.md) を参照。

## 2. 初回実装範囲

右クリック → 現在の求人票の抽出 → 3区分判定 → 確認・修正画面 → 再判定、までを実装する。

対象は、利用者が開いたHTTP(S)ページのメインフレームである。右クリックで起動した時点のタブを対象とし、
後でアクティブになった別タブへ取得対象を切り替えない。ページ内の右クリックメニューを起点とし、
タブバー上の右クリックは初回の対象外とする。

以下は初回実装に含めない。

- Google Sheets API連携・登録・認証
- 外部企業調査、検索、リンク先取得、自動巡回
- ローカルLLM・外部LLMによる分析
- 求人の採点・推薦・応募判断
- MHTML保存、OCR、PDF求人票、別フレーム内の求人本文の取得

拡張自身は外部通信を開始しない。元ページが通常の表示で行う通信とは区別する。

## 3. 利用フロー

1. 利用者が求人票と思われるページを開く。
2. ページ内で右クリックし、「この求人を調べる」を選ぶ。
3. 起動元タブからURL・タイトル・構造化データ・表示本文を取得する。
4. 項目を抽出し、求人票判定と企業名の特定状態を求める。
5. 独立した拡張タブに確認画面を表示する。
6. 利用者が判定理由・取得項目・不足項目を確認する。
7. 必要な項目を修正し、「再判定」を実行する。

初回実装は確認・修正結果の表示までで終了する。
「調べる」というメニュー名でも、この段階では企業調査を実行しない。

## 4. 合意済みの求人票判定仕様

- 現在のページが個別求人票かどうかを判定する。
- `JobPosting`構造化データがあれば優先して参照する。
- 構造化データがない場合、募集職種・仕事内容・応募資格・勤務地・給与・雇用形態などを組み合わせて判定する。
- 給与や勤務地がないことだけを理由に対象外としない。
- 求人一覧ページと個別求人詳細ページを区別する。
- 判定結果は「求人票」「判定保留」「対象外」の3区分とする。
- 判定理由と、取得できた項目・不足している項目を画面に表示する。
- 企業名を特定できない場合は、求人票であっても企業調査を保留する。
- 判定保留の場合は、利用者が抽出結果を確認・修正できるようにする。
- 対象外の場合は、外部調査とGoogle Sheetsへの登録を開始しない。
- 判定に使う情報は、原則として現在開いているページから取得する。

初回実装では、判定区分にかかわらず外部調査・Sheets登録を実行しない。

## 5. 抽出項目と根拠

| 項目 | 取扱い |
|---|---|
| 取得元URL・ページタイトル・取得時刻 | 起動元ページの識別情報として保持する |
| 企業名 | 雇用主を対象とする。求人媒体・紹介会社の名称を無条件に雇用主としない |
| 募集職種 | 個別求人の見出し・構造化データ等から取得する |
| 仕事内容 | 募集する仕事の説明として取得する |
| 応募資格 | 必須・歓迎条件を、取得可能な範囲で保持する |
| 勤務地・給与・雇用形態 | 原文を保持する。不明な値を推測で補完しない |
| 応募導線 | 応募・エントリー等の有無を補助的な根拠とする |
| 一覧・複数求人の兆候 | 求人カード、異なる職種・企業の反復等を保持する |

項目ごとに値と取得元（構造化データ、本文、利用者修正）を区別する。

根拠となる短い原文または構造化データ内の位置を保持し、画面で確認できるようにする。
取得できない項目は空文字による推定値ではなく、未取得として扱う。

ページ全文・HTML全体を恒久保存することは初回の要件としない。必要な項目と根拠に取得範囲を絞る。

## 6. 判定方針

### 6.1 構造化データ

初回はJSON-LDの `JobPosting` を対象とする。単一オブジェクト、配列、`@graph` に含まれる候補を確認する。
Microdata・RDFaは初回必須としない。

`JobPosting`の存在だけでは求人票と確定しない。表示中の主な求人と対応するか、一覧・関連求人のデータでないかを確認する。

複数候補がある場合、主な個別求人を特定できればその候補を使い、特定できなければ判定保留とする。
構文不正のJSON-LDで全処理を中断せず、本文による判定へ進み、その旨を理由に記録する。

### 6.2 本文による判定

単語の出現数だけでなく、募集職種と仕事内容が同一の個別求人に属しているかを確認する。
会社名・所在地だけの会社概要、給与に言及した記事、応募リンクがあるだけのページを求人票と確定しない。

| 区分 | 基本条件 |
|---|---|
| 求人票 | 表示内容と対応する個別のJobPostingを確認できる、または募集職種・仕事内容と募集条件や応募導線の組合せから個別求人を確認できる |
| 判定保留 | 求人の可能性はあるが根拠不足、複数候補で主対象が不明、構造化データと本文が矛盾する等 |
| 対象外 | 求人一覧・検索結果・一般記事・会社概要などで、個別求人の内容を確認できない |

一般的な応募資格が記載されていない求人もあり、単一項目の欠落を一律の除外条件にしない。
単純なキーワードだけで確定できない場合は保留にする。具体的な判定条件はテストケースと対応させて実装する。

### 6.3 企業名の扱い

求人票の判定結果と、企業調査に必要な企業名の特定状態を別に保持する。

- 求人票で企業名が特定できる：求人票として表示する。初回実装はここで終了する。
- 求人票だが企業名が不明・曖昧：求人票の区分は保持し、「企業調査は保留：企業名を確認してください」と表示する。
- 判定保留：抽出結果の確認・修正と再判定を待つ。
- 対象外：理由を表示する。外部調査・登録へ進めない。

企業名の文字列が埋まっているだけで、法人の同一性を外部確認済みとは扱わない。

## 7. 確認・修正画面

画面には以下を表示する。

- 取得元URL・ページタイトル・取得時刻
- 判定区分と判定理由
- 取得項目と取得元・根拠
- 未取得項目と、判定・企業名特定のために確認が必要な項目
- 企業名の特定状態と保留理由
- 修正欄、「再判定」、修正のリセット操作

元の抽出値と利用者の修正値を別々に保持し、利用者が修正した項目には印を付ける。
修正後の値をページ由来の情報として表示しない。利用者による修正は、外部情報源で確認した事実とは扱わない。

再判定では区分・理由・不足項目・企業名の状態を更新する。
企業名を入力しただけで、求人一覧や一般記事を自動的に求人票へ変更しない。初回は利用者が判定区分だけを直接上書きする機能を設けない。

対象外でも判定理由を確認できる画面を表示する。取得失敗は対象外と混同せず、エラーとして表示する。

## 8. 状態管理と例外

- 起動ごとに識別子を付け、複数タブの取得結果・修正値を混在させない。
- 取得時のURLを保持し、取得中に別ページへ遷移した場合は結果を採用せず再実行を案内する。
- 拡張画面・Chrome内部ページ・アクセスできないページは取得不可として案内する。
- 結果と修正値は拡張のセッション内で保持する方針とし、永続的な求人履歴は初回に作らない。
- セッション終了や拡張再読み込み等で結果が消える場合は、再取得が必要であることを利用手順に記載する。
- Webページ由来の文字列を確認画面でHTMLとして実行しない。

## 9. 構成と責務

| 予定ファイル | 責務 |
|---|---|
| extension/manifest.json | MVP専用のManifest V3定義。contextMenus・activeTab・scripting・storageを基本権限とする |
| extension/background.js | メニュー登録、起動元タブの指定、処理の進行、確認画面への引き渡し |
| extension/extract-page.js | ページ内情報と根拠の取得 |
| extension/classify.js | 入力情報に対する副作用のない判定処理 |
| extension/review.html / review.js / review.css | 結果表示、修正、再判定 |
| tests/ / tests/fixtures/ | 合成ページと自動テスト |
| package.json | テスト実行設定 |

判定処理はChrome APIや画面操作から分離する。将来の企業調査・Sheets登録は、確認済みの項目を受け取る別の処理として追加できるようにするが、今回その処理やダミー通信を実装しない。

## 10. 検証と完了条件

| ケース | 期待結果 |
|---|---|
| 表示内容に一致する単一JobPosting | 個別求人として判定し、根拠を表示 |
| 構造化データなし、職種・仕事内容・募集条件あり | 本文から個別求人を判定 |
| 給与・勤務地の一方または両方が欠落 | 欠落のみでは対象外にしない |
| 求人一覧・検索結果 | 個別求人と誤確定せず、対象外と理由を表示 |
| 関連求人のJobPostingを含む一般記事 | 構造化データの存在だけでは求人票にしない |
| 複数JobPostingで主対象不明 | 判定保留 |
| 求人らしいが本文不足 | 判定保留 |
| 企業名不明の個別求人 | 求人票の区分と企業調査保留を併記 |
| 壊れたJSON-LD | 本文へフォールバックし、処理が継続する |
| 利用者が項目修正 | 原抽出値を保持し、再判定で理由・不足項目が更新される |
| 複数タブから起動 | 各結果・修正値が混在しない |
| 起動元タブの遷移・閉鎖、取得権限不足 | 別ページの値で代替せずエラーを表示 |
| HTML風文字列を含む抽出値 | 画面で文字列として表示し、実行しない |
| 初回実装の全フロー | 外部調査・LLM・Sheets登録の通信を開始しない |

自動テストで抽出・判定・修正後の再判定を確認する。Chrome上の手動確認で、
右クリック起動・実ページからの取得・確認画面・修正・再判定までを検証する。

合成ページの成功を、全求人媒体での抽出精度保証とは扱わない。

完了条件は、上記ケースを検証し、起動から確認・修正までが動作し、
Spikeの既存ファイルを変更せずにMVPを独立して読み込めることである。
