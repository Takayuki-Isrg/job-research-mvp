# ローカルLLM分析：条件別評価

更新日：2026-11-08

## 今回の範囲

既存の求人票抽出・求人票／判定保留／対象外の3区分判定・確認・修正・再判定・リセットを維持する。今回変更するのは次の3点に限る。

1. 分析時点の採用情報をLLMで書き直さず直接表示する。
2. 希望条件ごとの評価表を表示する。
3. 確認事項を条件の優先順に並べる。

自由文の求人要約・特徴・懸念点の生成は条件別評価へ置き換える。A〜D評価、外部企業調査、Google Sheets API連携、外部LLM API、自動応募・自動除外は実装しない。

## 操作と比較条件

1. 求人票を右クリックして確認画面を開き、抽出内容を確認する。
2. 編集した場合は「修正して再判定」を押す。未反映の編集がある間は分析しない。
3. モデル一覧を取得してローカルモデルを選ぶ。選択モデル名だけを `chrome.storage.local` の `localLlmModel` に保存し、新しい確認タブや再起動後にも復元する。未導入の保存モデルを別モデルへ自動変更しない。
4. 希望条件を1行に1条件で入力し、「比較する条件を確認」を展開する。行ごとの条件ID・分類・外部調査対象を確認する。複数の条件を1行にまとめない。
5. 「ローカルLLMで分析」を押し、採用値の出所、条件別判定、根拠の意味を確認する。

対応する見出しは「探す職種（優先順位）」「ハード条件」「除外条件」「注意点（…）」「企業単位の指定」「評価・調査のルール」「希望条件」。見出しのない行は希望条件とする。「除外：」「ハード：」「職種：」「希望：」「注意：」「外部調査：」でも行を分類できる。「プロフィール」「あなたのプロフィールとして照合している内容」以降は応募者情報として分け、求人の根拠にはしない。

比較条件が0件の場合は、原因（未入力／見出しの行だけ／プロフィール見出し以降の行だけ）に応じて案内する。「希望条件：」のように見出しだけの行は条件として扱わない。

入力プレビューでは、次の行に注意を表示する（警告のみで、分割・修正・記号除去・再分類はせず、分析も止めない。判断は利用者が行う）。

- 「、」「。」「；」「／」等で区切られた2文字以上の内容が複数ある行：複数条件の可能性。文末の句点だけや数字の桁区切り（4,500,000）では警告しない。区切りのない複数条件は検出しない。
- 上記のうち、年収下限・固定残業・残業のルール照合の対象になり得る行：ルールが適用されると同じ行の他の内容は評価されない可能性。
- 行頭の「・」「-」「1.」等の記号の後に「除外：」等が続く行：接頭辞として認識されず、分類と優先順位は見出し由来または「希望」になる。「外部調査：」の場合は、口コミ等のキーワードがなければ外部調査の対象にもならない。条件文はそのまま判定に渡すため、LLMやルール照合が意図を読み取る場合はある。見出しの分類と接頭辞が同じ場合は警告しない。

警告がある行数は入力欄の下に、行ごとの内容は「比較する条件を確認」に表示する。

希望条件は2,000文字、求人の採用値との合計は6,000文字、比較条件は40行まで。超過を黙って切り捨てない。これは自由文のすべての意味を自動分解する機能ではないため、分類・行の分割結果は利用者が確認する。

## 抽出値・修正値・採用値

- 元の `record.snapshot.fields` は上書きしない。修正値は `record.overrides`、再判定の採用値は `record.assessment.values` に保持する既存方式を維持する。
- 分析入力のversionは2。分析対象ID、元ページ取得時刻、7項目の採用値、希望条件、比較条件とプロフィールを保存する。
- 各項目のprovenanceには元の抽出値、修正値（修正がなければnull）、採用値、採用元、抽出元の区分、抽出時の根拠を保存する。採用値が対応する抽出値・修正値と一致するか確認する。
- 画面に「分析時点の採用情報」を直接表示し、各項目で抽出値・修正値・採用値を展開できる。採用元は「元ページ抽出」「利用者修正」「採用元未確認」。元ページ由来でも抽出の正確性・内容の事実性は未保証であり、修正値を求人原文の事実として表示しない。
- 採用値、出所、希望条件の変更後は過去の分析として表示する。分析中の変更も検知し、以前の入力に対する結果で現状を上書きしない。比較はストレージ内のオブジェクトキー順に依存しない。

## 条件別評価表

各行は、比較した希望条件のID・全文・分類、判定、判定理由、判定方式、根拠ID、取得元項目、該当箇所、採用元を表示する。根拠箇所は展開できる。修正由来なら「求人原文として未確認」と明示し、元の抽出値も併記する。

| 判定 | 意味 |
| --- | --- |
| 一致 | 採用情報に条件を満たす根拠があると評価した。事実の保証ではない |
| 不一致 | 採用情報が希望条件に反する、または利用者の除外条件に該当すると評価した |
| 提示額次第 | 明記された年収範囲が希望下限をまたいでおり、実際の提示額の確認が必要 |
| 要確認 | 求人の採用情報を確認したが、判定を確定する根拠が不足している |
| 未調査 | 評価に必要な外部情報源への調査・照合を実施していない |

口コミ・報道・5ch・企業回答・従業員数等の照合条件は未調査とする。求人にリモート可否や納期が記載されていないことは、外部未調査とは区別して要確認とする。外部調査を実行したような結果は表示しない。

## 根拠の検証と限界

採用値を300コードポイントごとの断片に分け、`項目名:連番` の根拠ID、項目名、開始・終了位置、文字列、採用元を付ける。本文は切り捨てない。IDの有効範囲はその分析入力内であり、別の求人や再分析をまたいだ恒久IDではない。

LLMには採用値の断片と出所、比較条件、応募者プロフィールを送る。URL、HTML全体、未採用の元抽出値や修正履歴は送らない。保存する分析入力には履歴を残し、画面で確認できるようにする。

コードで次を確認する。

- 条件IDが入力に存在し、全条件が各1回だけ評価されている。
- 判定区分、理由・質問の形式が正しい。
- 返されたすべての根拠IDが存在する。ルール判定で補正する行に含まれた不正IDも拒否する。
- 参照先の項目・位置・文字列・採用元が分析入力と一致する。
- 根拠IDのない一致・不一致・提示額次第は、確定させず「根拠不足補正」により要確認にする。存在しないIDを返した結果は全体を拒否し、前の分析を維持する。
- ルール照合を使わない行で、外部調査でない条件への「未調査」、給与（年収・給与・月給・報酬）以外の条件への「提示額次第」は、その行だけ「判定区分補正」により要確認にする。LLMが返した根拠IDは、検証を通過したものなのでそのまま残す（根拠不足補正では根拠なし）。両方に該当する場合（給与以外の提示額次第で根拠なし）は判定区分補正とし、補正理由は両方残す。
- 補正した行は `correction` に補正前の判定・LLMの元の理由・元の質問・補正理由を保存し、評価表の「補正前：…」から確認できる。補正しない行とルール照合の行は `correction: null`。この項目を導入する前に保存した結果には `correction` がない。
- 条件IDの重複・欠落・未知ID、件数不一致、5区分以外の判定値、存在しない根拠IDなど、条件と評価の対応や入力形式を保証できない誤りは補正せず、全体を拒否する。

根拠が判定を意味的に裏付けるかは完全自動検証しない。実在する根拠を選んでも解釈が誤っている可能性があるため、利用者が原ページと照合する。

検証に失敗した場合は、確認画面の分析ステータスに期待件数・受信件数、重複・欠落・未知の条件ID、不正な項目の位置と理由をまとめて表示する。例えば26条件に対して26件返っても、IDが重複していれば重複IDと欠落IDを表示し、全体を拒否する。根拠なしの確定判定と、条件に使えない判定区分（上記）は要確認へ補正し、それだけでは検証エラーにしない。

詳細は求人の確認画面のDevTools Consoleにも出力する（Service WorkerのConsoleではない）。構造検証エラーは `AnalysisValidationError` とし、`details` に `stage`、`expectedCount`、`receivedCount`、`duplicateIds`、`missingIds`、`unknownIds`、`issues`（項目の位置・理由）を持つ。診断情報には求人本文・希望条件全文・LLM応答全文を含めない。

## コード側の限定的な照合

- 除外条件に案件アサイン／客先常駐があり、仕事内容の採用値に「顧客先にて案件アサイン」と明記されていれば不一致とする。契約種別をSESや無期雇用派遣と自動断定する処理ではない。
- 納期条件について、仕事内容の採用値に納期・締切の記載がなければ要確認にする。「短納期の可能性がある」とは生成しない。
- 「年収○万円以上」と、給与に明記された単一の年収範囲を比較する。希望額をまたぐ範囲は提示額次第、範囲全体が下回れば不一致、下限が満たせば一致。月給×12や賞与を使った補完は行わない。対応しない表記や範囲の逆転は要確認とする。
- 固定残業時間の明確な表記と「○時間以上を除外／不一致」という条件を比較する。時間不明なら要確認。
- その他の残業条件は、原文を表示したうえで平均・上限・固定残業の意味を要確認とする。「残業20時間」を「残業20時間以内」と書き換えない。

これはあらゆる求人表記に対応する数値解析ではない。複数の給与範囲、表記ゆれ、否定・条件付き表現、会社グループの同一性などは利用者が確認する。採用値の出所に関係なく同じ照合をするが、利用者修正由来の判定はその旨を表示する。

## 確認事項の優先順位

条件IDと判定を付けて、除外条件 → ハード条件 → 職種 → その他の希望 → 注意点 → 外部調査の順に並べる。同順位は入力順を保つ。要確認の行に質問がない場合は条件文から確認案内を作る。外部調査対象は入力上の分類にかかわらず外部調査として最後に並べる。調査・応募は自動実行しない。

## 通信・保存・互換性

接続先は `http://127.0.0.1:11434` に固定。`/api/tags`と`/api/show`でローカルGGUFの文章生成モデルを確認し、クラウドモデルは拒否する。モデルの取得・作成やサーバー設定の変更は行わない。

確認タブからストリーミング応答を読む。温度0、コンテキスト8192、生成上限は条件数に応じて1,024〜4,096トークン。条件数が多い場合は従来より出力・時間が増える場合がある。待機上限は3分で、所要時間の予測ではない。上限到達・不完全出力を成功扱いにしない。経過時間と実際の所要時間を表示する。

分析は明示操作のみ。対象外・判定保留では実行しない。結果と入力は求人と同じ `chrome.storage.session` に保存し、確認画面を閉じたら既存方式で削除する。失敗しても抽出値・修正値・前回分析を維持する。旧形式の分析は再実行を案内し、新形式として誤表示しない。文字列はHTMLとして実行しない。

## 接続許可の設定

PC上ではOllamaの起動と `gemma3:4b`・`gemma3:12b` 等の導入を確認した。APIへ拡張Originを付けてアクセスすると403となったため、Ollama側のOrigin許可が必要である。既存のOllama設定・プロセスは自動で変更していない。

1. 更新後の拡張を再読み込みし、求人票から確認画面を開く。
2. 分析欄の「接続情報」で、この拡張の `chrome-extension://拡張ID` を確認する。
3. Windowsのユーザー環境変数 `OLLAMA_ORIGINS` に、このOriginを末尾の `/` なしで追加する。既存値があれば保持してカンマ区切りで追加する。
4. Ollamaアプリをタスクトレイから終了し、起動し直す。これは利用中の他のOllama処理を止める場合があるため、利用者がタイミングを選ぶ。
5. 「Ollamaのモデル一覧を取得」を押し、モデルを選んで分析する。

全拡張へのワイルドカード許可やLANへの公開は必要ない。ローカル専用運用をサーバー側でも固定する場合は、Ollama公式の `OLLAMA_NO_CLOUD=1` 設定を使用できる。

Manifestのhost権限は `http://127.0.0.1/*`。Chromeのhost権限はポート単位で制限できないため、実際の送信先をコードとCSPでポート11434に限定する。本番のRAサイトへの常時アクセス権限は追加しない。

## 手動確認が必要な項目

1. 拡張をリロードし、実際のRA求人の右クリックから起動する。自動テストでは一時拡張コピーのテスト用入口を使うため、ネイティブ右クリックとactiveTabの確認とは区別する。
2. 全希望条件を貼り付け、「比較する条件を確認」で行の分割・分類・プロフィール分離が意図どおりか確認する。必要なら条件を行に分ける。
3. 評価理由を、参照IDだけでなく原ページの該当箇所と照合する。要確認・未調査・利用者修正の表示が適切か確認する。
4. 実求人で給与・仕事内容などを修正して再判定・再分析し、採用値の反映、元の抽出値、以前の分析の区別を確認する。
5. 使用するモデルと全条件での所要時間、長文時の出力完了、再試行時の安定性を確認する。12BのCUDA初期化失敗の解消や全モデルの品質は今回の検証対象外。
